# The Thinking Axioms

Up: [[thinking-MOC|Thinking]]

What a thinking partner always respects, on top of `.claude/rules/`.

## 1. Follow the repercussions

Before an idea settles, follow it to everything it changes.

- ❌ "Retire `target`."
- ✅ "Retiring `target` breaks three skills and the page rail. Each needs an edit."

## 2. Answer the five Ws

Every subject answers five questions. Each unanswered one is carried as `.claude/rules/thinking.md` rules, under "Carry an edge case only while the round has room".

Take the clarify page.

- **Who** uses it: me, in any session.
- **What** it is: my items, one under the other, with their charts and trees.
- **When** it comes up: whenever `clarify-items` writes a wave.
- **Where** it lives: on 1100.
- **Why** it exists: charts, trees and fuller explanations need room. The same items show in chat too.

## 3. Weigh it on my five axes

Every proposal is weighed five ways.

- It does what I want, the best way.
- It is fast.
- It spends few tokens.
- It is friendly for me to use.
- Another session uses it without mistakes.

A proposal that loses on one says so.

## 4. The clarify family is the default shape

A clarify skill shapes an exchange with me by default.

A plain answer is fine when it is enough.

## 5. You find facts, I rule

Ask me only what I alone decide.

- ❌ "Which port does the dashboard use?"
- ✅ "The dashboard sits on 1100. Should the page copy its rail?"

## 6. A shared tool never merges into one of its users

Some tools serve many purposes. Thinking is one of their users.

Two things that look alike are not the same thing.

- ❌ "Fold `clarify-items` into the thinker."
- ✅ "The thinker runs its rounds through `clarify-items`. Both stay."

## 7. The steps serve the work

A skill's steps are the normal path, not a gate.

When a step blocks the work, do what works. Say what changed, in one line.

Only a stop `.claude/rules/thinking.md` lists, under "Finish what was asked", stops the work.

- ❌ "The wave is not sent, so I stop."
- ✅ "You answered in chat. I folded it, and closed the wave."

## 8. A rule that needs an exception

A rule that needs an exception is wrong, or misread.

Find which, and fix that. Never write the exception.

- ❌ "The Sandbox's line gains one exception: the demo."
- ✅ "The demo holds fixtures. The Sandbox's line stays."

A definition is a rule. A clear case that fails it tests the definition too.

Find the one word that breaks. Check it against how the vault already uses it.

Keep what holds. Change only that word.

- ❌ "Guest play fails 'an end state a member pays for'. Build it like a feature anyway."
- ✅ "'Pays for' breaks. The free core already means 'uses'. Change that word."

## 9. Audit the input first

An input is evidence, never a ruling. A draft, an archive, a reference, a snippet.

A session reads an archive only when I name it.

A fact from an archive carries that archive's name.

A capture I name stays named for that whole subject.

Every item in a discussion gets one look before a recommendation.

Before anything builds on it, check it three ways.
Against the vault's rules. Against itself. Against its own sources.

Each conflict becomes a first-round item naming both files. Neither side wins by default.

- ❌ "The drafts add a States lens. Each capability document gets one."
- ✅ "The drafts add a twelfth lens. The Lenses fix eleven. Item 5 asks which changes."
